# Profile file

`$FACTORY_HOME/profile.md` maps every capability in `capabilities.md` to a
concrete tool. A front door writes it (`intake-oss` by discovery; a vendor
front door ships a hand-written one and copies it in). Every run stamps the
profile name into `status.json.profile`, and the heartbeat uses the stamped
profile when it runs passes for that run.

## Shape

```markdown
# Profile: <name>            # discovered | <vendor name>
generated: <iso time>  by: <front door>  harness: claude-code | cursor | codex

## Harness
mcp_prefix: mcp__hub__       # how `mcp:` tools are addressed in this harness; empty when tools are bare.
                             # Several servers: one `  <server>: <prefix>` line each plus `  default: <prefix>`
agent: yes | no              # Agent tool available
skill: yes | no              # Skill tool available
loop: yes | cron | no        # /loop skill, CronCreate only, or neither
tools_present: gh rg …       # optional: CLIs found on PATH
manifests: …                 # optional: build and CI files seen in the cwd repository

## tracker
tool: mcp:tracker_get_issue | cli:gh issue view {key} --json ... | file
auth: ok | missing | unknown
ops:                         # one line per operation the engine needs, only where the default is not obvious
  create: mcp:tracker_create_issue
  children: jql `parent = {key}`
  hierarchy_level: issuetype.hierarchyLevel
  transition: in_progress=In Progress, in_review=In Review, done=Done
notes: |
  Free text the skills read before using this capability: hierarchy, label
  names, project conventions, host patterns.

## sources
tool: mixed
hosts:
  docs.example.com: mcp:docs_get_content (resolve shortlinks first)
  docs.google.com: skill:docs-fetch
  "*": builtin:WebFetch

## chat
tool: mcp:chat_send_message | none
self: U0123ABC              # own user id for DMs
reply_prefix: ""            # text prepended to every reply the factory posts

## code
tool: mcp:code_search + cli:rg

## pr
tool: cli:gh
connect: mcp:connect_pr | none
comment_prefix: "(🤖 bot) " | ""
branch_prefix: bot- | ""
body: skill:<vendor pr body skill> | builtin:pr-template

## ci
tool: mcp:ci_* | cli:gh run | none
root_cause: cli:<ci tool> errors --url {url} | skill:<ci diagnosis skill> | none
flake_patterns: <path to a markdown file with vendor patterns> | none

## obs
tool: ... | none
signals: <path to a markdown file with vendor metric recipes> | none
## deploy
tool: ... | none
## incidents
tool: ... | none
## dispatch
tool: mcp:create_thread+create_session | builtin:worktree+Agent | none
## knowledge
tool: ... | none
## design
tool: ... | none
## voice
tool: skill:<vendor prose skills> | builtin:prose

## Gaps
- <capability>: <what is missing and what the factory does instead>
```

## Rules

- Every capability section exists, even when `tool: none`.
- `auth:` is filled from a read-only probe when one exists (`gh auth status`,
  a `whoami`-style tool). `missing` is a gap.
- `notes:` is where vendor knowledge lives. Engine skills quote nothing
  vendor-specific; they read `notes:` at run time.
- Any section may carry `auth:`, `ops:` (operation → tool overrides) and
  `notes:`; the shape above shows them only where they are usual. Unknown
  keys are ignored by the engine, so discovery may record extra facts.
- A profile is regenerated by the front door's `config rediscover`, or when
  a tool call fails with an unknown-tool error. Engine skills never edit it.
- Vendor front doors may ship extra data files next to the profile (flake
  patterns, metric names, hierarchy notes). The profile points at them by
  absolute path so the engine can read them without knowing the vendor.
